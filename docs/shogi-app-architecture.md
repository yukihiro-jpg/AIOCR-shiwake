# 将棋研究アプリ 構成案

作成: 2026-08-23 / 対象: 「AI解説つき棋譜研究＋定跡・囲い学習」アプリ

---

## 0. 結論（先に3行）

1. **エンジンとAIの役割を厳密に分ける。** 指し手・評価値・変化手順は必ず将棋エンジンが出し、AIは「エンジンが出した事実を日本語に翻訳する係」に徹する。AIに手を考えさせた瞬間、それらしいウソを言い始めて研究の役に立たなくなる。
2. **エンジンは差し替え可能なアダプタの裏に置く。** ①ブラウザ内WASM（どこでも動く・軽い）②自宅PCのローカルUSIブリッジ（水匠/dlshogiをフルパワーで）③既存GUIが解析済みの棋譜を読み込むだけ、の3系統を同じインターフェースで扱う。
3. **リポジトリは業務スイートと分ける。** 技術的な理由がある（後述の COOP/COEP 問題）。業務データと個人研究を混ぜないためでもある。

---

## 1. 要求の整理

いただいた要望を実装単位に割ると4つになります。

| # | 要望 | 実装単位 | 難易度 |
|---|---|---|---|
| A | 棋譜の局面ごとに「この手の意図・有力手・次点・変化」を自然言語で解説 | 解析→ファクト抽出→AI解説 | 中（設計が肝） |
| B | 自分が考えた手を「こういう流れになるから駄目/良い」と添削 | 強制探索(`searchmoves`)＋咎め手順の言語化 | 中 |
| C | 普通の棋譜並べ＋評価値チャート | 棋譜パーサ＋盤UI＋分岐ツリー＋グラフ | 低〜中（作業量は多い） |
| D | 定跡・囲い・囲い崩しの学習 | 囲い判定器＋定跡DB＋問題集＋学習履歴 | 中（コンテンツ制作が本体） |

**Cが土台**です。CだけでもShogiGUI等の解析済み棋譜を読めば成立するので、ここから作るとエンジン統合を後回しにできます。

---

## 2. いちばん重要な設計判断：エンジンとAIの役割分離

### やってはいけない構成

```
棋譜 → AI（「この局面どう指す？」） → 解説
```

LLMは将棋の探索器ではありません。合法手でない手、存在しない変化、根拠のない評価値を、自信満々の日本語で出力します。研究用途では致命的です。

### 正しい構成

```
局面 → 将棋エンジン（探索）→ ファクト抽出（プログラム）→ AI（日本語化）→ 検証 → 表示
                                                              ↑
                                                    ここでウソを弾く
```

AIに渡すのは **構造化された事実のJSONだけ**。プロンプトで「与えられた手順以外の指し手を書くな」「評価値は与えられた数値をそのまま使え」と縛り、さらに **出力に含まれる指し手表記を機械的に拾って、合法手かつ与えたPVに含まれるかを検証** します。検証に落ちた文は表示せず再生成するか、警告つきで出す。

この「AIは翻訳者、検証は機械」という一線が、このアプリの品質をほぼ決めます。

## 4. 層ごとの設計

### 4.1 エンジン層（EngineAdapter）

**すべてのエンジンを1つのインターフェースに寄せます。** これをやっておかないと、後からdlshogiを足すときにUI側まで書き換えることになります。

```ts
// src/lib/engine/types.ts
export interface AnalysisRequest {
  sfen: string;               // 局面
  moves?: string[];           // 追加の指し手（USI形式）
  multiPv?: number;           // 候補手を何本出すか（既定3〜5）
  limit: { nodes?: number } | { depth?: number } | { movetime?: number };
  searchmoves?: string[];     // ★この手だけを読ませる（ユーザー手の添削で使う）
}

export interface PvLine {
  rank: number;               // 1 = 最善
  scoreCp?: number;           // 歩=100 換算。手番側視点
  mateIn?: number;            // 詰みまでの手数（+なら手番側の勝ち）
  depth: number;
  pv: string[];               // USI形式の読み筋
}

export interface EngineAdapter {
  readonly id: string;        // 'wasm-yaneuraou' | 'local-bridge' | 'imported'
  readonly displayName: string;
  init(): Promise<void>;
  analyze(req: AnalysisRequest): AsyncIterable<PvLine[]>;  // 途中経過を流す
  stop(): Promise<void>;
  dispose(): Promise<void>;
}
```

`analyze` を **AsyncIterable にするのが要点**です。USIエンジンは `info` 行を出し続けるので、深さが上がるたびにUIを更新できます（既存ソフトの検討ウィンドウと同じ挙動）。

#### ① ブラウザ内WASM

- やねうら王のWASM移植（`@mizarjp/yaneuraou.halfkp` / `.k-p`、npm最終公開 **2022年6月**）。更新は止まっていますが、USI準拠のエンジンとして動作し、棋力は学習用途には十二分です。
- **制約1: SharedArrayBuffer が要る** → `Cross-Origin-Opener-Policy: same-origin` と `Cross-Origin-Embedder-Policy: require-corp` が必要。GitHub Pages はヘッダを設定できないので **`coi-serviceworker`**（Service Workerでヘッダを注入する定番回避策）を使う。
- **制約2: これがサイト全体に効く**。COEP を有効にすると、CORP ヘッダを返さない外部リソース（CDNのスクリプト、外部画像など）が全部ブロックされます。→ **業務スイートと同じオリジンに置いてはいけない理由**（5章）。
- **制約3: 評価関数ファイルが重い**（数十MB級）。初回だけ取得して Cache API / IndexedDB に保存し、2回目以降はローカルから読む設計にする。
- スマホでは重いので、ノード数を絞った「ざっくり評価」モードを用意する。

#### ② ローカルUSIブリッジ（本命）

自宅PCの水匠やdlshogiをそのまま使う方式。小さなNodeプロセスを1つ立てるだけです。

```
[ブラウザ] --WebSocket--> [bridge (Node)] --stdin/stdout--> [水匠.exe / dlshogi]
                            ・127.0.0.1 のみバインド
                            ・起動時トークンでアクセス制限
                            ・Origin チェック
```

- USIは行指向のテキストプロトコルなので、ブリッジは実質「WebSocketと標準入出力を繋ぐだけ」の100行程度で済みます。
- **接続方式の注意**: HTTPSページ（GitHub Pages）から `ws://127.0.0.1` へ繋ぐのは、原則 localhost が例外扱いされて通りますが、ブラウザ側の締め付け（Private Network Access 等）が年々入っており将来も保証はできません。
  → **ブリッジ自身がアプリのHTMLも配信する**構成（`http://127.0.0.1:8899/` でアプリを開く）にしておくと完全に同一オリジンになり、将来壊れません。**PCで本気の研究をするときはこちら、外出先や他端末ではGitHub Pages版＋WASM、と使い分ける**のが現実解です。
- 配布は `npx` 一発、または単一実行ファイル化。

#### ③ 解析済み棋譜インポート（Phase 0で効く）

ShogiGUI等で「棋譜解析」をかけた結果は、KIF/CSAのコメントに評価値と読み筋が入ります（CSAは `'**` 始まり、KIFは `*` コメント行が慣例。ソフトごとに書式が微妙に違う）。

- **これを読むだけで評価値チャートが再現でき、エンジン無しでもアプリが成立します。**
- 書式差に耐えるよう、**評価値パーサはプラグイン方式**（ソフト別に正規表現セットを持つ）にしておく。
- 他ソフトの画面画像やコードの流用はライセンス上できません。「チャートをそのまま流用」は、**解析結果データを取り込んで自前で同じ形のグラフを描く**という形で実現します。

### 4.2 ファクト抽出層（このアプリの心臓）

エンジンの生出力のままAIに投げても、良い解説にはなりません。**AIが解説に使える「材料」をプログラムで揃えます。**

```ts
export interface PositionFacts {
  ply: number;
  sideToMove: 'black' | 'white';
  sfen: string;

  // 直前の手の評価
  playedMove?: {
    usi: string;
    ja: string;              // ☗７六歩（tsshogi が生成）
    scoreBefore: number;     // 指す前の評価値
    scoreAfter: number;
    loss: number;            // 最善手との差（cp）
    verdict: 'best' | 'good' | 'inaccuracy' | 'mistake' | 'blunder';
  };

  // 候補手（MultiPV）
  candidates: Array<{
    usi: string; ja: string;
    scoreCp?: number; mateIn?: number;
    pvJa: string[];          // 読み筋を日本語棋譜に変換したもの
    lossFromBest: number;
  }>;

  // 局面の客観的特徴（＝AIの語彙になる部分）
  material: { black: number; white: number; diff: number };
  handPieces: { black: string; white: string };
  castle: { black: CastleMatch | null; white: CastleMatch | null };
  opening: { name: string; confidence: number } | null;  // 戦型判定
  book: { name: string; movesIn: number; theory: string } | null; // 定跡DBヒット
  kingSafety: { black: number; white: number };  // 玉周りの利き差など
  threats: {
    inCheck: boolean;
    mateFound?: { side: 'black' | 'white'; moves: number };
    hangingPieces: string[];      // タダ取りされる駒
  };
  phase: 'opening' | 'middlegame' | 'endgame';
}
```

ポイント:

- **`pvJa`（読み筋の日本語化）は tsshogi にやらせる。** AIに「7g7f を日本語にして」とやらせると必ず間違えます。
- **`verdict` の閾値はコード側で決める。** 「悪手」の定義をAIに委ねると回ごとにブレます。目安: 損失 <30cp=最善級 / <100=好手 / <300=疑問手 / <700=悪手 / それ以上=大悪手（要調整）。
- **詰み・詰めろ判定は重い。** 完全な詰めろ判定は「相手の全合法手について詰み探索」が必要で終盤専用です。中盤は評価値と玉の安全度で代用し、終盤フェーズに入ったら `go mate` を回す、という段階分けにする。

### 4.3 解説生成層（Claude）

#### 呼び出し方

既存の業務スイートと同じく **ブラウザから直接叩けます**（`komon`/`souzoku` が実績あり）。新規のReactアプリなら公式SDKを使うのが素直です。

```ts
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic({
  apiKey: localStorage.getItem('shogi-anthropic-key') ?? '',
  dangerouslyAllowBrowser: true,   // ブラウザ直叩きの明示的な許可
});
```

- APIキーは端末の localStorage（業務スイートと同じ流儀。同期しない）。
- **モデルIDはハードコードせず設定画面で選ばせる**（komonの `claudeModel` 設定と同じ形）。「一括解説は軽量モデル、深掘りは最上位モデル」と使い分けられるようにする。
- **必ずストリーミング**にする。解説が数百字出るまで無言だと体感が非常に悪い。
- **必ずタイムアウトを付ける**（業務スイートの不変条件4と同じ規律）。
- **AIの応答が空でも、ユーザーの入力や既存の解説を消さない**（同上）。

#### プロンプト設計

システムプロンプトは **固定**（＝プロンプトキャッシュが効く）。ここに入れるもの:

- 役割定義:「あなたは与えられた探索結果を日本語に翻訳する解説者。自分で手を考えてはいけない」
- 将棋用語集と言い回しの型（「〜と来られると」「〜が利いているので」等）
- 出力フォーマット（構造化出力で `{ summary, intent, mainLine, alternatives[], warning }` を強制）
- 禁止事項:「与えられた手順に無い指し手を書かない」「評価値は与えられた数値をそのまま使う」「断定できないことは書かない」

ユーザーメッセージは `PositionFacts` のJSONだけ。**局面ごとに変わる部分を後ろに置く**ことでキャッシュ前方一致が保てます（システムプロンプトが1024トークンを超えていればキャッシュ対象になる。用語集を入れれば自然に超える）。

#### 出力検証（必須）

```ts
function validateCommentary(text: string, facts: PositionFacts): ValidationResult {
  // 1. 「７六歩」「同銀」等の日本語棋譜表記を抽出
  // 2. tsshogi で局面に対する合法手か判定
  // 3. facts.candidates[].pvJa のいずれかに含まれるか判定
  // 4. 落ちたものを violations として返す
}
```

違反があれば1回だけ再生成し、それでも駄目なら「AIの解説は生成できませんでした（エンジンの読み筋のみ表示）」に落とす。**黙って表示しないこと。**

#### キャッシュ

`(sfen, engineId, 探索条件, モデル, プロンプト版数)` をキーに、**解析結果と解説の両方を IndexedDB に保存**します。

- 同じ棋譜を何度も並べ直しても課金されない
- オフラインでも過去の解説が読める
- プロンプトを改良したら版数を上げて作り直す

### 4.4 棋譜・盤・チャート層

| 部品 | 方針 |
|---|---|
| 棋譜モデル | **tsshogi**（sunfish-shogi製、2026-06更新の現役）。KIF/KI2/CSA/JKF/SFEN/USI の読み書き、分岐、消費時間、コメント、日本語棋譜生成、合法手判定まで一通り入っている。 |
| 文字コード | KIF/KI2 は **Shift_JIS が多い**。tsshogi は変換機能を持たないので `encoding-japanese` で前処理する（業務スイートに既に入っている依存）。 |
| 盤UI | 自作を推奨（SVGまたはCSS Grid）。ドラッグ＆ドロップ、成/不成ダイアログ、駒台、反転、直前手ハイライト、候補手の矢印オーバーレイ。既存の盤ライブラリ（`kifu-for-js` 等）は再生特化で、こちらが必要な「候補手矢印」「局面編集」まで賄えない。 |
| 棋譜ツリー | 分岐を木で表示。**本譜と検討手順を同じデータ構造で持つ**（ユーザーが試した手も分岐として保存される＝あとで見返せる）。 |
| 評価値チャート | 自作SVG。横軸=手数、縦軸=評価値（±2000程度でクリップし、詰みは天井に張り付かせる）。クリックで該当局面へジャンプ、疑問手にマーカー。**複数エンジンの結果を重ね描き**できると研究用として強い。 |

### 4.5 学習コンテンツ層（定跡・囲い・囲い崩し）

ここは**コードよりコンテンツが本体**です。仕組みを軽く、データを厚く。

#### 囲い判定器

```ts
interface CastleTemplate {
  id: string;              // 'mino' | 'anaguma-ibisha' | 'yagura-kin' | ...
  name: string;            // '美濃囲い'
  kingSquare: string;      // 先手基準の玉位置（必須条件）
  pieces: Array<{ sq: string; piece: string }>;  // 先手基準の駒配置
  derivesFrom?: string[];  // 発展元（舟囲い→左美濃→天守閣美濃）
  weakPoints: string[];    // 急所のマス（囲い崩しの解説に使う）
}
```

- 判定は **一致率スコア**（玉位置一致を必須条件、残り駒の一致率でランキング）。後手は180度回転して同じテンプレートを使う。
- 一致率0.7以上なら「（発展途上）」付きで表示。1.0で完成形。
- 30種類ほど定義すれば実用になります（矢倉各種・美濃各種・穴熊各種・舟囲い・elmo・中住まい・雁木・地下鉄飛車…）。
- **`weakPoints` を持たせるのがポイント**。「穴熊の急所は端と1段目」といった知識をAI解説の材料として渡せます。

#### 定跡

2種類を分けて持ちます。

1. **定跡DB（機械用）**: やねうら王形式の定跡ファイル（SFENをキーに指し手・評価値・出現回数を並べたテキスト）を変換して使う。丸ごとはWebには重いので、**序盤N手まで**に絞って SFENハッシュで分割したJSONにし、必要な塊だけ fetch する。
2. **戦型ノート（人間用）**: 「角換わり腰掛け銀」「四間飛車vs居飛車穴熊」等の解説文＋主要変化。局面から戦型を判定して該当ノートを表示。**下書きはClaude Codeで作り、エンジンで検証し、自分で直す**（後述）。

#### 囲い崩し問題集

```ts
interface Problem {
  id: string;
  sfen: string;
  sideToMove: 'black' | 'white';
  solution: string[];          // USI形式の正解手順
  tags: string[];              // ['穴熊崩し', '端攻め', '継ぎ歩']
  targetCastle: string;        // 'anaguma-ibisha'
  difficulty: 1 | 2 | 3 | 4 | 5;
  explanation: string;
  engineVerified: {            // ★自動検証の結果を必ず持たせる
    at: string; engine: string; depth: number;
    solutionIsBest: boolean; scoreGain: number;
  };
}
```

**作問パイプライン（ここでClaude Codeを使う）**:

```
プロ棋譜/自分の棋譜を大量に投入
  → エンジンで全局面解析
  → 「囲いが判定でき、かつ評価値が大きく動いた手」を候補として自動抽出
  → Claude Code でテーマ分類・解説文の下書きを一括生成
  → エンジンで「正解手順が本当に最善か」を自動検証（落ちたら破棄）
  → 人が最終確認 → problems/*.json としてコミット
```

これは**ローカルのバッチ処理**なので、実行時のAPI課金とは無関係です。**「実行時＝Claude API、コンテンツ制作時＝Claude Code」と分けるのが、ご要望の"クロードコード連携"の正しい形**だと考えます。

#### 学習履歴

間違えた問題、疑問手を出した局面、苦手なタグを蓄積し、「あなたは穴熊崩しの端攻めで手数を損する傾向があります」といったコーチングをAIに書かせる。**これは他の将棋ソフトにない部分で、このアプリを作る価値そのものです。**

### 4.6 永続化層

| データ | 置き場所 | 理由 |
|---|---|---|
| 棋譜・分岐・コメント | IndexedDB | 量が多い |
| 解析キャッシュ・AI解説キャッシュ | IndexedDB | 量が多い・端末ローカルで十分 |
| 問題集・定跡・囲い定義 | リポジトリ内の静的JSON | バージョン管理したい |
| 学習履歴・進捗 | IndexedDB ＋ 任意でFirebase RTDB同期 | 端末を跨ぎたければ |
| APIキー・エンジン設定・表示設定 | localStorage | 端末ローカルが正しい（同期しない） |

Firebase同期を付けるなら、業務スイートと**同じ合言葉方式は使わないこと**（別アプリなので別の合言葉・別ノード）。個人利用なら最初は同期なしで十分です。

## 5. 置き場所：業務スイートとは分ける

**別リポジトリ（例: `shogi-lab`）を新規作成し、GitHub Pages の別URLで配信することを推奨します。**

技術的な理由（こちらが決定的）:

- WASMエンジンを動かすには `coi-serviceworker` で **サイト全体に COOP/COEP を掛ける**必要がある。
- COEP を有効にすると、CORP ヘッダを返さないクロスオリジンのリソースが全部ブロックされる。
- 業務スイートは **pdf.js を CDN から遅延読込**しており（komonの納付税額確認書解析）、Google Drive連携のGISスクリプトも外部から読んでいる。**ほぼ確実に壊れます。**

運用上の理由:

- 顧問先データを扱う業務アプリと、個人の趣味研究アプリを同一URL・同一デプロイパイプラインに乗せると、片方の変更が片方を壊すリスクとレビュー負荷が増える。
- 業務スイートの `check-invariants.mjs` の不変条件（per-clientノード、STORAGE_KEY_MAP等）は将棋アプリには一切当てはまらず、ノイズになる。

※どうしても1リポジトリにまとめたい場合は、`/shogi` を **別ドメイン or 別Pagesサイト** として切り出し、WASMエンジンを諦めて②ローカルブリッジ／③インポート専用にする、という妥協はあり得ます。

## 8. コストとレイテンシの見積り

**AI解説は1局面あたり 入力2〜4千トークン／出力500〜800トークン**程度になります。全120手を全部解説すると1局で数百円規模になり、現実的ではありません。以下の3段構えで抑えます。

1. **オンデマンド**: ユーザーが「解説して」を押した局面だけ。
2. **疑問手だけ自動**: 一括解析で `verdict` が inaccuracy 以上になった局面（1局あたり10〜15局面）に絞る。
3. **キャッシュ**: 同一局面・同一プロンプト版なら再課金しない。

さらに:

- **プロンプトキャッシュ**でシステムプロンプト（用語集込み）を使い回す。読み込みは約1/10のコストになる。TTLは学習セッション向けに長め（1時間）を選べるようにする。
- **モデルを設定で切り替え可能**にし、「一括解説は軽量モデル・深掘りは最上位モデル」を選べるようにする（業務スイートの無料/有料キー使い分けと同じ思想）。
- **エンジン解析はAPI課金ゼロ**。ここを厚くして、AIは「言語化が必要なところだけ」に使うのが正しい設計です。

レイテンシ:

- エンジン解析（WASM・数十万ノード）: 0.5〜2秒
- AI解説（ストリーミング開始まで）: 1〜3秒
- → **先にエンジンの候補手と評価値を出して表示し、AI解説は後追いで流し込む**。業務スイートのカード明細解析と同じ2段構えです（「AIを待ってから表示する設計にしない」）。

## 9. 落とし穴リスト（先に知っておくこと）

1. **AIに指し手を考えさせない。** これを破ると全部台無しになります。設計の一線。
2. **AI出力の指し手は必ず合法手チェックを通す。** 検証なしで表示しない。
3. **COEPはサイト全体に効く。** 業務スイートと同居させない理由。
4. **KIFはShift_JIS。** UTF-8前提で読むと文字化けします。
5. **完全な詰めろ判定は重い。** 終盤フェーズ限定にする。
6. **評価値の符号。** USIの `score cp` は**手番側視点**。チャートは先手視点に統一する必要があり、ここは高確率でバグります。テストを書く場所。
7. **`mate` スコアの扱い。** 巨大な数値としてグラフに入れると軸が壊れる。天井に張り付かせる専用処理を入れる。
8. **WASMエンジンの評価関数ファイルは重い。** 初回DLの進捗表示とキャッシュを最初から作る。
9. **`multipv` を上げるほど探索は弱くなる。** 候補手表示用（multipv=5）と最善手判定用（multipv=1）を分けて考える。
10. **エンジン解析結果は非決定的**（スレッド数・時間で変わる）。キャッシュキーに探索条件を含めないと「昨日と違うことを言う」アプリになります。
11. **他ソフトのUI・コード・定跡ファイルの流用はライセンス確認が要る。** 「チャートを流用」は自前描画で実現する（4.1③）。
12. **APIキーがブラウザに露出する**のは業務スイートと同じ前提。個人利用なら許容ですが、**一般公開するなら絶対に別方式**（サーバ経由）が必要です。

## 付録: ユーザーの手を添削する仕組み（要望B）

```
1. ユーザーが盤上で手を指す（またはUSI/日本語棋譜で入力）
2. tsshogi で合法手チェック
3. エンジンA: 通常探索（multipv=3）→ 最善手と評価値 best
4. エンジンB: searchmoves <ユーザーの手> で強制探索 → user
5. loss = best.score - user.score
6. user.pv = ★これが「咎められる手順」＝相手の最善の反撃
7. ファクト抽出 → Claude へ:
     { ユーザーの手, loss, 咎め手順(日本語), 最善手, 最善手順(日本語),
       局面の特徴（囲い・駒得・玉の安全度） }
8. 出力例:
   「☗２四歩は取り込みを狙う自然な一手ですが、☖同歩☗同飛に☖８六歩から
     逆に先攻されます(-420)。この局面では☗６八玉と一手囲いを進めるのが
     優ります(+30)。攻め合いには自陣の整備が足りていません。」
9. 出力検証 → 表示
```

`loss` の大きさで文体を切り替える（loss<50なら「有力です」、>500なら「これは危険です」）と、解説の説得力が上がります。**判定はコード、言語化だけAI** という原則がここでも効きます。
